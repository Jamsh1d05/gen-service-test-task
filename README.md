# Сервис генерации

Принимает заказ на генерацию, списывает токены, отправляет задачу провайдеру и при отказе идёт к
следующей «ноге». Если отказали все ноги, возвращает токены. Каждое движение денег происходит ровно
один раз: при дублях вебхуков, при гонках между 4 процессами и при падениях.

Стек: Python 3.12, FastAPI, PostgreSQL 16, SQLAlchemy 2 (async, asyncpg), Alembic, httpx, pytest.

## Быстрый старт

```bash
docker compose up --build        # db → migrate (одноразово) → app (uvicorn --workers 4), alpha, beta
```

| Сервис | Адрес                      |
|--------|----------------------------|
| app    | http://localhost:8000/docs |
| alpha  | http://localhost:8001      |
| beta   | http://localhost:8002      |
| db     | localhost:55432 (gen/gen)  |

Порты переопределяются через `APP_PORT`, `DB_PORT`, `ALPHA_PORT`, `BETA_PORT`. Таймаут сторожа
задаётся через `PROVIDER_TIMEOUT` (по умолчанию 60 с).

Пример сценария:

```bash
python scripts/pay.py 1 100                       # подписанный вебхук оплаты, создаёт пользователя 1
curl -s localhost:8000/generate -H 'content-type: application/json' \
     -d '{"user_id":1,"model_slug":"image-fast","prompt":"cat","ref_images":[]}'
curl -s localhost:8000/tasks/<task_id>
curl -s localhost:8000/users/1/balance
```

Регистрации нет. Пользователь считается внешней сущностью и создаётся при первой оплате.

## Тесты

Тесты ходят в настоящий PostgreSQL из compose. Они сами создают базу `gen_test` и накатывают на неё миграции.

```bash
# внутри сети compose, ничего ставить не нужно
docker compose up -d db
docker compose run --rm tests                 # интеграционные тесты (31)
docker compose up -d && docker compose run --rm tests -m e2e   # e2e по живому стеку (4 воркера)

# или с хоста
uv sync
uv run pytest                                 # TEST_DATABASE_URL по умолчанию -> localhost:55432/gen_test
uv run pytest -m e2e                          # нужен поднятый `docker compose up`
```

Обязательные тесты:

| Требование                                                | Тест                                                                    |
|-----------------------------------------------------------|-------------------------------------------------------------------------|
| 20 одновременных одинаковых оплат → одно начисление        | `tests/test_payments.py::test_20_concurrent_identical_payments_credit_once` |
| 10 одновременных `failed` на последней ноге → один возврат | `tests/test_failover.py::test_10_concurrent_failed_webhooks_on_last_leg_refund_once` |
| Отказ первой ноги → успех на второй, две попытки           | `tests/test_failover.py::test_first_leg_fails_task_completes_on_second` |
| Поздний `completed` после сторожа (правило 6)              | `tests/test_watchdog.py::test_late_completed_*` (оба варианта)          |

Кроме них проверяются:

- 400, 402, 404 и 429, включая гонку из 8 одновременных `/generate` при лимите 3;
- синхронные 503 и таймаут;
- пропуск ноги по `skip_on_moderation` и отказ `payload`;
- вебхук, пришедший раньше ответа 202;
- сторож, запущенный «в 4 процессах».

После **каждого** теста автоматически проверяется инвариант `users.balance = SUM(ledger.amount)`.

Сторож в тестах не ждёт 60 секунд. Тест сдвигает `deadline_at` попытки в прошлое и вызывает `watchdog.tick()`.
Это та же логика, что крутится в фоне, только без ожидания.

E2E-тесты (`tests/e2e`) проверяют то же самое на настоящем стеке: 4 процесса uvicorn и фейковые
провайдеры по HTTP. Поведение провайдеров переключается через `PUT /_behavior`.

## Архитектура

```
app/
  api/            HTTP: схемы, проверка подписи, роуты. Без бизнес-логики.
  services/
    generation    POST /generate: проверки, списание, задача + первая попытка в одной транзакции
    orchestrator  машина состояний задачи: единственное место, где попытка переводит задачу дальше
    dispatcher    отправка попытки провайдеру; синхронная ошибка уходит обратно в orchestrator
    watchdog      таймаут молчащих попыток; результат тоже уходит в orchestrator
    payments      идемпотентное начисление по payment_id
    queries       чтение для GET-эндпоинтов
  domain/
    routing       чистые функции выбора ноги (правила 1–5), unit-тесты без БД
  providers/      шлюз к провайдерам (Protocol + HTTP-реализация; в тестах подменяется фейком)
  container.py    composition root: сборка зависимостей
fake_providers/   фейковый провайдер; один код, запускается как alpha и как beta
migrations/       Alembic; схема, ограничения, триггеры, каталог
```

Главный принцип: **вебхук с отказом, синхронная ошибка и сторож сводятся к одному вызову
`Orchestrator.resolve(attempt_id, outcome)`**. Поэтому правила 2–4 реализованы в одном месте, и
гарантии «ровно один раз» тоже нужно обеспечить только в одном месте.

### Модель данных

- `users(balance)`: проекция журнала, её обновляет **только триггер** на вставку в `ledger`.
- `ledger`: журнал операций, только добавление (UPDATE/DELETE запрещены триггером).
  Виды записей `topup`, `charge`, `refund`; CHECK следит за знаком суммы и обязательными ссылками.
- `payments`: входящие оплаты, `credited_at` отмечает факт начисления.
- `gen_models`, `legs`: каталог, засеян миграцией `0002`.
- `tasks`: статус `processing | completed | failed`, `current_attempt_id`, цена на момент заказа.
- `attempts`: попытки (история для `GET /tasks/{id}`).
  Статусы `sending → accepted → completed | failed | timed_out | cancelled`, плюс `deadline_at`,
  `late_result_url` и `late_result_at`.

### Жизненный цикл задачи

1. `POST /generate`: одна транзакция. Под `SELECT … FOR UPDATE` строки пользователя проверяются
   подходящие ноги (400), число активных задач (429) и баланс (402). Затем пишется `charge` в
   журнал, задача и первая попытка в статусе `sending` с `deadline_at = now() + PROVIDER_TIMEOUT`.
   После commit отправка к провайдеру идёт в фоне, ответ клиенту не ждёт сеть.
2. Dispatcher вызывает `POST /tasks` у провайдера и передаёт `reference_id` (id нашей попытки) и `callback_url`.
   - `202`: попытка становится `accepted`. Это условный `UPDATE … WHERE status='sending'`, так что
     пришедший раньше вебхук не затирается.
   - 5xx или ошибка соединения: `resolve(failed, technical)`.
   - Таймаут: `resolve(timed_out)`. Провайдер мог принять задачу, поэтому его поздний
     результат обрабатывается по правилу 6, а не теряется.
3. Вебхук провайдера ищет попытку по `(provider, external_id)` или по `reference_id`. Второе нужно,
   если вебхук обогнал ответ 202 или мы так и не узнали `external_id`. Затем вызывается `resolve`.
4. `resolve` выбирает следующую ногу (`domain.routing`): `technical` и таймаут ведут на следующую ногу,
   `moderation` тоже, но пропускает ноги с `skip_on_moderation`, `payload` сразу завершает задачу.
   Если ног не осталось, задача `failed` и пишется `refund`.

## Чем обеспечено «ровно один раз»

Гарантии держатся на PostgreSQL, а не на памяти процесса. Каждая из них продублирована вторым
барьером на уровне схемы.

**Начисление (оплата).**

1. `INSERT INTO payments … ON CONFLICT DO NOTHING`, затем `SELECT … FOR UPDATE` этой строки.
   Все параллельные доставки одной оплаты, в том числе из разных процессов, выстраиваются в
   очередь на одной строке.
2. Начисляет только та, что увидела `credited_at IS NULL` и `status = succeeded`. Она в той же
   транзакции пишет `topup` в журнал и ставит `credited_at`. Остальные отвечают `already_credited`.
3. Второй барьер: уникальный индекс `ledger(payment_id) WHERE kind='topup'`. Даже при ошибке в коде
   второе начисление не пройдёт.
4. Повтор той же оплаты с другой суммой или другим пользователем получает 409, деньги не меняются.

**Возврат.**

1. `resolve` берёт `SELECT … FOR UPDATE` строки задачи и **под этой блокировкой** перечитывает
   попытку. Действует, только если попытка ещё «в полёте» (`sending`/`accepted`) и является текущей.
2. Первый из 10 параллельных `failed` переводит попытку и задачу в терминальный статус и пишет `refund`.
3. Остальные девять после снятия блокировки видят `failed` и отвечают `ignored`.
4. Второй барьер: уникальный индекс `ledger(task_id, kind) WHERE kind IN ('charge','refund')`.
   Второй возврат по задаче физически невозможен. То же для списания.
5. Ещё один барьер: `UNIQUE (task_id) WHERE status IN ('sending','accepted')`. У задачи не бывает
   двух попыток в полёте, а значит, и двух параллельных веток, ведущих к возврату.

**Баланс равен сумме журнала (правило 8).** Код вообще не пишет в `users.balance`. Его меняет
`AFTER INSERT` триггер на `ledger` в той же транзакции. `CHECK (balance >= 0)` страхует проверку
на 402, а UPDATE/DELETE журнала запрещены триггером.

**Лимит 3 активные задачи.** Счётчик проверяется под блокировкой строки пользователя, поэтому
параллельные `/generate` одного пользователя из разных процессов идут строго по очереди. Тест
отправляет 8 одновременных запросов и получает ровно 3 × 202 и 5 × 429.

## Сторож в 4 процессах

Сторож запущен в каждом воркере, лидера нет. Раз в `WATCHDOG_INTERVAL` он выбирает попытки
с истёкшим `deadline_at` и для каждой вызывает `resolve(timed_out)` в режиме сторожа:

- блокировка задачи берётся с `FOR UPDATE SKIP LOCKED`. Если задачу сейчас обрабатывает другой
  процесс (вебхук или сторож), этот процесс её пропускает и не ждёт;
- под блокировкой проверяется, что попытка всё ещё активна и дедлайн действительно прошёл.

Поэтому одну попытку таймаутит ровно один процесс, остальные получают `skipped`. Это проверено
тестом, где 4 `tick()` идут параллельно, и вручную на стеке: в логах 4 воркеров ровно одна строка
`timed out`. Время берётся из БД (`clock_timestamp()`), так что расхождение часов между процессами
ни на что не влияет.

## Что будет при падении процесса посреди обработки вебхука

Вся обработка вебхука — одна транзакция: статус попытки, статус задачи, строка `refund` и новая
попытка. Частичного состояния не бывает.

| Где упали | Что произойдёт |
|-----------|----------------|
| До commit | Транзакция откатывается, провайдер не получил 2xx. Настоящий провайдер повторит вебхук, и повтор обработается штатно. Если повтора не будет, попытка останется активной, и по `deadline_at` её подберёт сторож любого живого процесса. Деньги не теряются, хуже всего — задержка до `PROVIDER_TIMEOUT`. |
| После commit, до ответа | Провайдер повторит вебхук, `resolve` увидит терминальную попытку и ответит `ignored`. Повторного возврата не будет. |
| После commit, до отправки следующей ноги | Новая попытка уже записана в статусе `sending` с дедлайном. Сторож затаймаутит её и поведёт задачу дальше по правилам 2–4. Задача не зависнет, деньги не задвоятся. |
| Посреди `/generate` после commit | Аналогично: попытка `sending` с дедлайном, сторож доведёт задачу. |
| Посреди вебхука оплаты | Транзакция откатывается, платёжка повторит. Начисление идемпотентно по `payment_id`. |

Сетевые вызовы никогда не выполняются внутри открытой транзакции. Поэтому зависший провайдер не
держит блокировки и соединения пула.

## Правило 6: поздний `completed`

Ситуация: сторож (или синхронный таймаут) уже признал попытку неудачной (`timed_out`), а потом
провайдер всё-таки прислал `completed`. Деньги по задаче к этому моменту уже двигались максимум
один раз (списание и, возможно, возврат). Поздний результат **не должен порождать нового
движения денег**. Решение зависит от того, где сейчас задача.

1. **Задача ещё `processing`** (сторож перевёл её на следующую ногу, та ещё работает).
   **Принимаем поздний результат**: задача становится `completed` с этим `result_url`, текущая
   попытка на другой ноге переводится в `cancelled`, её будущий вебхук будет `ignored`. Возврата не
   было и не будет: пользователь заплатил один раз и получил результат раньше, чем дождался бы
   следующей ноги. Попытка помечается `completed` с `late_result_at`, так что в истории видно,
   что результат пришёл после таймаута.
2. **Задача уже терминальна**: `failed` с возвратом или `completed` через другую ногу.
   **Задачу не трогаем.** Результат сохраняется в `attempts.late_result_url` и `late_result_at`
   (аудит и ручной разбор), вебхук получает `late_discarded`. Мы сознательно не делаем «выдать
   результат и списать токены заново»:
   - пользователю уже сообщили о неудаче и вернули деньги;
   - эти токены он мог потратить, и повторное списание может не пройти;
   - деньги начали бы двигаться задним числом, вопреки «ровно одному разу».

   Стоимость ресурса провайдера в этом случае берёт на себя сервис.

Итог: задача никогда не получает одновременно и результат, и возврат. В варианте 1 возврата нет,
в варианте 2 нет результата. Это проверяют тесты `test_late_completed_while_task_still_running_is_accepted`
и `test_late_completed_after_refund_is_discarded`. Поздний `failed` после таймаута всегда игнорируется.

## Фейковые провайдеры

`fake_providers/app.py`: `POST /tasks` сразу отвечает `202 {"external_id"}`, вебхук приходит через
2–20 с и подписан `X-Signature = HMAC-SHA256(body, WEBHOOK_SECRET)`. Поведение задаётся env-переменными
`FAKE_*` или во время работы через `PUT /_behavior`:

| Параметр | Что делает |
|----------|------------|
| `min_delay`, `max_delay` | задержка вебхука |
| `failure_rate`, `failure_type` | доля отказов и тип: `technical`, `moderation`, `payload`, `random` |
| `sync_failure_rate`, `sync_failure_mode` | синхронный отказ: `503` или `timeout` (зависание, задача при этом всё равно выполняется) |
| `duplicate_rate` | вебхук отправляется дважды одновременно |
| `drop_rate` | вебхук не приходит совсем |
| `late_rate`, `late_delay` | `completed` приходит через `late_delay` секунд, позже `PROVIDER_TIMEOUT` |

```bash
curl -X PUT localhost:8001/_behavior -H 'content-type: application/json' -d '{"failure_rate": 1}'
```

## Миграции

Схема создаётся только миграциями Alembic (`migrations/versions`). ORM-модели лишь отображают
таблицы. Ограничения, индексы и триггеры описаны в миграциях явным SQL, потому что именно на
них держатся гарантии.

- `0001_schema`: таблицы, CHECK-и, частичные уникальные индексы, триггеры журнала.
- `0002_seed_catalog`: каталог `image-fast` и `video-long` с ногами.

В compose миграции применяет отдельный одноразовый сервис `migrate` (`alembic upgrade head`), а
`app` стартует только после его успешного завершения. Так 4 воркера не применяют DDL наперегонки.

```bash
# применить вручную
DATABASE_URL=postgresql+asyncpg://gen:gen@localhost:55432/gen uv run alembic upgrade head
uv run alembic downgrade -1          # откат на одну ревизию
uv run alembic history

# добавить следующую
uv run alembic revision -m "add priority to tasks"   # создаст migrations/versions/<rev>_add_priority_to_tasks.py
# заполнить upgrade()/downgrade() (op.add_column(...) или op.execute("...") — по одному SQL-оператору
# на вызов, asyncpg не принимает несколько операторов в одном prepared statement), затем:
uv run alembic upgrade head
```

Новую модель или ногу каталога тоже стоит добавлять отдельной миграцией, по образцу `0002`.

## API

| Запрос | Ответ |
|--------|-------|
| `POST /generate` `{user_id, model_slug, prompt, ref_images}` | `202 {task_id}`; 400 нет подходящей ноги (до списания), 402 мало токенов, 404 модель/пользователь, 429 уже 3 активные задачи |
| `POST /webhooks/providers/{name}` `{external_id, reference_id?, status, result_url?, error_type?}` | `200 {result}` (`completed`, `retrying`, `failed`, `late_accepted`, `late_discarded`, `ignored`); 401 неверная подпись; 404 неизвестная попытка |
| `POST /webhooks/payments` `{payment_id, user_id, tokens, status}` | `200 {result}` (`credited`, `already_credited`, `recorded`); 401; 409 тот же `payment_id` с другими данными |
| `GET /tasks/{id}` | статус, `result_url`, `current_leg`, история попыток (провайдер, статус, тип ошибки, время) |
| `GET /users/{id}/balance?limit=20` | баланс и последние строки журнала |
